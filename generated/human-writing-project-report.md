## 一、项目理解

### 1.1 这个 Skill 是什么

human-writing 是一个通用中文创作与改稿 Skill，覆盖知乎回答、论坛长帖、公众号、博客、小说、对白、口播等场景。它的目标只有一句话，让读者感觉对面有一个具体的人。这个人知道一些事，也有不知道的地方，愿意讲细节，敢下判断。

作者卡兹克在发布文中给出了它诞生的理由。他四月份开源过「卡兹克文风写作.skill」，后来意识到那个方案的根本缺陷在于过于固化，用户只能写成四个月前的卡兹克。他认为写作辅助这件事应该有基石、有方法论、有放之四海皆有效的准则，Skill 的职责是帮用户发现自己，而不是把用户改造成作者本人。于是他向中文系朋友讨教，把内部写作 Skill 蒸馏成通用规则，手写了部分文档，形成这个版本。

### 1.2 仓库结构

```
human-writing/
├── SKILL.md              唯一入口，编排全部规则
├── references/
│   ├── forum-prose.md    长帖散文的说话关系与节奏
│   ├── reality.md        现实写作的事实边界
│   ├── fiction.md        虚构创作规则
│   ├── revision.md       改稿规则（留到初稿后读）
│   └── formats.md        特殊形式（口播、剧本、诗歌等）
├── scripts/check_prose.py 禁令检查脚本
├── agents/openai.yaml    分发配置
├── dist/human-writing-lite.md 精简分发版
├── LICENSE / VERSION
```

关键设计是 SKILL.md 只做编排，详细规则按文体命中才加载。这与发布文中的判断一致，「现在的模型在纯粹的写作能力上越来越难约束，写作这块你得不断加约束，效果才会更好」。加约束的方式不是一次全灌，而是分层、按需、按时序。

### 1.3 核心设计哲学

SKILL.md 第 10 行给出活人感的优先级，这条线贯穿整个 Skill。

> 活人感首先来自材料，其次来自说话位置，最后才是语气。

发布文用中国传统文章学做了对应的表述，义理（你想说什么）、考据（你的判断有什么事实支撑）、辞章（怎么写得准确有力）。过去去 AI 味的努力几乎全部押在辞章上，而 AI 文章真正的病根在前两者是空的，观点属于平均意义上的所有人，细节属于概率，只有署名属于你。《周易》的「修辞立其诚」说的就是这件事。

仓库把这套哲学落成了四个可执行的机制。

1. 材料门槛先于提纲。非虚构一千二百字以上的稿子，先在内部列出至少五件具体材料并注明来路，列不出就不动笔。
2. 说话位置先于文字。动笔前在内部回答五个问题（谁在说、为什么现在想说、有什么材料、判断到哪里为止、读者会追问什么），答案不进成稿。
3. 规则按需加载。四个参考文件按任务命中读取，revision.md 固定留到初稿之后。
4. 脚本硬校验。check\_prose.py 执行成稿禁令（冒号、破折号、翻案句、黑话），失败打回重改直到清零。

## 二、对话任务全景

本次对话共完成六个递进任务，全部围绕把一个抽象的 Skill 变得可看、可学。

### 任务一 高层架构图

**目标** 分析仓库，用 Archify 生成系统架构图，展示 8-12 个核心组件、一条主请求路径、外部依赖、信任边界，细节放卡片。

**动作** 通读 SKILL.md 与 references，识别出 SKILL.md 编排核心、五个参考规则文件、检查脚本、分发产物等组件，定义主路径（用户 → Agent → SKILL.md → 规则 → 成稿 → 修订 → 检查 → 交付）。

**坑** 首次验证报仓库 origin 不匹配，本地是 fatcatfy 镜像，spec 里写的是 KKKKhazix 原仓库。改成一致后通过。

**产物** human-writing.architecture.json、human-writing-architecture.html

### 任务二 架构说明文档

**目标** 用户看不懂架构图，生成解释文档。

**产物** human-writing-architecture-explanation.md，逐组件、逐路径、逐边界讲解，把卡片内容与源文件行号对应。

### 任务三 整理 workspace

**动作** 把散落在根目录的生成物统一移入 generated/ 目录，检查 .gitignore 确认不会被误提交。

### 任务四 Skill 调用流程图

**目标** 用 Archify 可视化「一次 Skill 调用的过程」，用于学习。

**动作** 定义六条泳道（用户与交稿、编排与门槛、规则加载、写作执行、校验、材料不足处理），十二个节点，主路径加三条异常分支。这是本次对话工作量最大的一次，经历多轮验证修复，节点重叠、标签遮挡、连线穿节点、微短线，逐项诊断逐项修。

**产物** human-writing-skill-call.workflow\.json、human-writing-skill-call.html。九项检查全过，0 错误 0 警告。沙箱无 Chrome，浏览器截图级视觉检查跳过，结构校验完整。

### 任务五 解读「先定位说话位置」

**目标** 用户追问写初稿前内部定位说话位置这一环节怎么理解。

**要点** 从三个层面回答。它解决什么问题（先确定人再产生文，多数 AI 味的病根是没有主体）；为什么是内部的（答案是写作输入而非交付物，类似演员的角色小传）；它同时是诚信边界（四种合法说话位置，亲历、调查、行业熟悉、认真查资料，不能把查资料写成亲历）。定位环节同时承担材料校验，第三问答不出就触发回退。

### 任务六 流程图迭代，标注文件交互

**目标** 在每个流程节点标注涉及的文件，并标明是读取、执行还是无文件。

**动作** 十二个节点的 sublabel 与 tag 全部更新（如「读取 · 入口与编排规则」「初稿后读 revision.md」「执行 check\_prose.py」「无新文件」），新增「文件与脚本」卡片收纳节点放不下的完整路径。

**坑** 这一轮遇到的约束最有学习价值。子标签在默认节点宽度下只有 84px 可读空间，超宽即报错；加宽节点又触发列距挤压（列距 130px，节点超宽互叠）和桌面可读性检查（viewBox 缩放后投影字号不得低于 6px）。最终方案是节点内只放短标注，完整文件清单下沉到卡片，信息不丢失、布局不破坏。

## 三、核心机制与原文观点的对照

| 发布文观点                    | 仓库落地                                                |
| ------------------------ | --------------------------------------------------- |
| AI 味的本质是「没有一个真实的人在里面生活过」 | 动笔前五问强制确立叙述者，材料五件强制注入真实来路                           |
| 义理、考据、辞章三者缺一，辞章再好也是空中楼阁  | 材料门槛管考据，说话位置管义理，check\_prose.py 管辞章                 |
| AI 会反问你要更多真实信息           | 追问用户节点，亲历型材料一次问完最多三问，问时不同时交稿                        |
| 鲁迅写孔乙己一个「排」字就够，不先做心理分析   | forum-prose.md 要求开头尽快碰到事情、推进靠材料和因果、删路标词             |
| 修辞立其诚                    | 现实稿来源红线（查资料不得写成亲历、猜测不得写成内幕）写进 SKILL.md 与 reality.md |
| 宁可短也不能凑                  | 材料不足时交六百字短答，篇幅是目标、材料边界是底线                           |

第三方实测文的两个案例佐证了这套机制的效果。让它模仿鲁迅，句子干净、隐喻完整，但读者仍然不知道是谁写的，这是只做辞章的天花板。让它以民工父亲的角度写日记，产出的是铁丝穿鞋、转账备注反复修改、把铃声音量调到最大这类由具体动作承担情绪的文本，这是材料与说话位置就位之后的样子。

## 四、可复用的学习到的内容

这一章是全部对话中沉淀下来、可以迁移到其他项目的经验。

### 4.1 Skill 设计层面

1. **入口只做编排，细节分层加载**。SKILL.md 不堆全部规则，五个参考文件按任务命中读取。上下文是稀缺资源，规则全部常驻会稀释注意力，还会互相打架（散文句法不该压到诗歌分行上）。
2. **按时序加载，不提前加载**。revision.md 留到初稿之后是全文最精妙的一条时序设计，动笔前读审稿规则会让作者自我审查，写作和修订分离各自发挥最大效力。
3. **把价值观变成可执行的关卡**。「真诚」是口号，「列不出五件材料就不动笔」是关卡。Skill 设计的关键动作是把抽象原则翻译成数量化、可判定的门槛（五件、三问、六百字）。
4. **先定人再定文**。任何生成任务先问谁在说话、凭什么知道、边界在哪。这条对写作之外的生成任务（代码评审、方案说明）同样成立。
5. **硬禁令用脚本兜底，软判断留给人**。check\_prose.py 只执行写明的硬禁令，警告项回到人工判断，脚本发现形状、人来判断有没有活人。工具边界划得清楚，才不会用机械规则糟蹋好文章。
6. **反例驱动写作**。SKILL.md 里大量「不能」写得极具体（把记录方便解释五遍仍然是三条材料、用户给三条抽象想法要一千字是高频错误）。具体的坑比抽象的准则有效。
7. **Skill 不建画像、不留后门**。不创建作者画像、不生成个人规则库、不自我繁殖新 Skill，交付物只有作品本体。一个被反复调用的 Skill 必须显式写清自己不做什么。

### 4.2 Archify 使用层面

1. **先写候选再调渲染，不在散文里规划坐标**。写完 spec 立即验证，验证器报什么就修什么，比预先心算布局快得多。
2. **泳道图的表达分工**。泳道表达职责（谁负责这一环），列表达时序（先做后做），异常泳道单独用 exception 变体，主线一眼可辨。
3. **微短线是布局错误的信号**。8px 以下的连线线段几乎总意味着两个节点挤在同一列或 sides 设错，与其调线不如动节点。
4. **标签宽度先于文案写作**。workflow 节点 sublabel 可用宽度有限（本例约 84px），先确认预算再写文案，超预算的内容下沉到卡片，卡片是收纳溢出信息的正确位置。
5. **一处诊断一处修复**。每轮只改验证器点名的那个 subject，改完重跑，不做顺手的全局重构。六轮迭代全部收敛靠的是这条纪律。
6. **成品冻结**。验证通过即冻结，后续需求（本次加文件标注）作为新一轮迭代重新走验证，而不是直接改 HTML。

### 4.3 工作方法层面

1. **读懂再画**。两次出图前都先通读 SKILL.md 与 references，图上的每个节点都能对应到源文件的行号。可视化是理解的输出，不是理解的替代。
2. **沙箱限制如实报告**。Chrome 不可用就明说视觉检查跳过，不用「应该没问题」糊弄。校验通过的部分和没验过的部分分开陈述。
3. **解释要分层**。用户看不懂图，补文档；用户追问单个环节，结合源码原文（带行号）讲透一层。文档跟着问题走，不一次性倾倒。
4. **生成物集中管理**。generated/ 目录隔离所有产物，.gitignore 确认，仓库保持干净。
5. **对「AI 味」本身的实操认识**。本对话产出的说明与报告都受这套规则潜移默化的约束，具体动作、来源可溯的判断、不重复解释、不喊口号。去除 AI 味不是删几个句式，是每一句都经得起「这是谁说的、他凭什么知道」的追问。
